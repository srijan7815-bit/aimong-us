## The station

Halcyon-9: 64×44 tiles (32 px), 10 named rooms — Bridge, Medbay, Hydroponics,
Reactor, Galley, Cargo Bay, Storage, Engine Room, Comms, Observatory — joined by
13 three-tile corridors. The generated room graph has **10 nodes, 13 edges, 4
independent loops** (Euler: E − V + 1) and is a single connected component. 1,465
walkable tiles (52% of the grid). 8 vent pairs (reciprocal), 12 task spots, 10
spawn points. Every room, vent, task and spawn is reachable from the first spawn
by walking; the generator refuses to write a map that fails those checks.

The blueprint is hand-authored rectangles in `scripts/gen-map.mjs`; nothing is
copied or traced from any commercial game (see THIRD_PARTY.md).

| Budget | Measured |
|---|---|
| Server tick **p95 < 10 ms** with 10 players walking | **p95 0.186 ms**, p50 0.078, p99 0.297, max 2.225 ms over 413 ticks at 19.82 Hz (`apps/server/scripts/perf-m2.ts`) |
| 3 clients walk smoothly, no rubber-banding | A 822 px, B 822 px, phone 284 px; peak speeds **127 / 136 / 166 px/s** against a 132 px/s walk speed — i.e. no correction ever read as a teleport |
| Walls block movement | pushed into a wall for 2.5 s → final position still on floor; 5,000 random steps in unit tests never enter a wall |
| Walls block vision + mask matches server | fog hash computed in the browser equals the server's `computeVisionMask` for all 3 clients (122 / 112 / 54 visible tiles) |
| Unit tests + smoke | **49 unit tests** (29 shared incl. 15 new world/vision, 20 server) and **22 smoke checks** — all pass |

## How movement works

1. The client steps its own pod with `stepPlayer()` — the *same* function the
   server runs — sub-stepped at 20 Hz, so a slow frame cannot slow the walk.
2. It sends `{seq,x,y}` at 20 Hz. The server keeps the latest input per session
   (500 ms TTL), applies it in its 20 Hz loop, and stamps the player's `seq`.
3. The client compares the server's position for that `seq` against its own
   history entry and applies the difference to both the prediction and the
   history. The *display* offset decays over ~45 ms instead of snapping.
4. Other players are drawn 90 ms in the past, interpolating between snapshots
   (the network delay is emulated at 120 ms on the phone client).

## Honest gaps / issues

- **`start` now opens a free-roam station** (walking only, no roles/tasks/kills).
  The button used to refuse with "arrives in M2"; the notice now says roles and
  tasks arrive in M3. It is not a playable round yet — do not read it as M3 done.
- **Frame rate in this sandbox is 4–11 fps** because Chromium runs on one software
  core here; the movement measurements above are therefore frame-rate independent
  (prediction is driven by real elapsed time), but I have **not** seen this on real
  hardware. The scene is a single pre-rendered terrain texture + one small canvas
  per frame, which should be cheap on a phone GPU.
- Two client bugs found and fixed during this milestone, worth knowing:
  smooth-follow camera-lag style lerping of the pod *never catches up* at low frame
  rates (replaced with a decaying offset), and sprite frames must be registered on
  the atlas texture or every `setCrop` drifts.
- Reconnecting mid-walk resyncs position instead of replaying history; a very long
  disconnect >48 px snaps (by design).
- Joint "one phone on real mobile data" was emulated (CDP: 120 ms RTT, 1.2/0.6
  Mbps), not tested on a physical phone.
- The map is one station; multi-map rotation is not in PLAN.md for M2.
